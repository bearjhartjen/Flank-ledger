# Flank Ledger

A small static website that turns **The Flank Ledger** — a plain Markdown file
of dated withdrawals and deposits — into a readable, browsable page.

The site is generated by `scripts/build.py`, which reads
`data/The Flank.md` and writes the finished pages into `site/`.

## The canonical workflow

The ledger is edited on the Desktop, **not** in the repository:

1. Edit `~/Desktop/The Flank.md`.
2. Within a couple of seconds, the **watcher** picks the change up: it copies
   the ledger into `data/The Flank.md`, rebuilds `site/`, and stages both.
   The edit is now waiting in GitKraken like any other change.
3. Open GitKraken, stage and commit.
   The `pre-commit` hook rebuilds the site and stages it again, so one commit
   always carries the ledger and the matching site.
4. Push.
   The `pre-push` hook refuses the push if the site fails to build.
5. GitHub Actions rebuilds `site/` and publishes it.

The file on the Desktop is the **source of truth**. `data/The Flank.md` in the
repo is only a synced copy; it is never edited directly. If the hook's build
step ever fails, the commit is blocked so a broken site is never published —
bypass it with `git commit --no-verify` (and fix the build first).

### Why the watcher is needed

The ledger lives outside the repository, so editing it on its own leaves the
repository looking clean — and a git GUI will not offer to commit when there
is nothing staged. The watcher bridges that gap. It only ever **stages**; it
never commits and never pushes.

If you would rather not run a background service, `sh scripts/sync-ledger.sh`
does the same job by hand, and the git hooks still work for any commit that
already has something staged.

## One-time setup

Run once per clone, from anywhere inside the repository:

```sh
sh scripts/install-hooks.sh    # the git hooks
sh scripts/install-watcher.sh  # the background watcher (systemd user service)
```

The hooks point git at the tracked `.githooks/` directory (`core.hooksPath`)
and also copy them into `.git/hooks/` as a fallback. Verify with:

```sh
git config --get core.hooksPath   # should print: .githooks
```

The watcher is a systemd user service, so it starts at login. Check it with:

```sh
systemctl --user status flank-ledger-watcher
journalctl --user -u flank-ledger-watcher -f
```

Remove it again with `sh scripts/uninstall-watcher.sh`.

Then finish the GitHub side:

1. Create the repository on GitHub (see the privacy note below).
2. Add the remote: `git remote add origin <your-repo-url>`.
3. Push: `git push -u origin main`.

That's it for the basic setup. The site is published by one of three
workflows, and you only need to enable one of them:

| Workflow | How it publishes | Extra setup |
| --- | --- | --- |
| `gh-pages.yml` | Pushes the site to a `gh-pages` branch, which GitHub serves automatically | **None** — works on a fresh repo |
| `pages.yml` | The official GitHub Pages deployment | Settings → Pages → Source → **GitHub Actions** |
| `cloudflare.yml` | Cloudflare Pages | Two repository secrets — see `CLOUDFLARE.md` |

`gh-pages.yml` is the zero-setup default. The other two are there if you
prefer them.

### If a workflow fails

Neither `pages.yml` nor `cloudflare.yml` fails the build when its one-time
setup is missing. They skip the publishing step and print what to do in the
job summary, so a red X in the Actions tab always means something real.

## Building and previewing locally

```sh
python3 scripts/build.py
```

Then open `site/index.html` in a browser.

To refresh the site **without** committing (for example, to check an edit
before pushing):

```sh
sh scripts/sync-ledger.sh
```

`sh scripts/sync-ledger.sh --check` reports what would change — whether the
ledger differs, how many transactions it holds, and where the site would be
written — without writing anything.

## Data privacy

The ledger is personal financial data. Keep the repository **private**, and do
not make the published site public.

There are two ways to publish, and they differ in cost:

| | GitHub Pages | Cloudflare Pages |
| --- | --- | --- |
| Workflow | `pages.yml` | `cloudflare.yml` |
| Works with a **private** repo? | Needs a paid plan | **Yes, on the free tier** |
| Extra setup | Settings → Pages → GitHub Actions | Two repository secrets — see `CLOUDFLARE.md` |
| Build time | — | Free tier allows 500 builds/month |

So: **if you do not want to pay for a GitHub plan, use the Cloudflare
workflow** — it is the one that keeps the repo private on the free tier.

- GitHub Pages on a **private** repository requires a paid plan (GitHub Pro or
  a Team/Enterprise plan). **Verify current pricing** — plan limits change, and
  this README does not track them.
- Note that a published site is reachable by anyone with the URL, even when
  the repository behind it is private. If that matters, treat the site URL as
  a secret, or add a password in front of it.
- The `gh-pages` branch workflow publishes the same way and is also affected
  by this: the **site** is public even if the repository is private.

## A note on silver

The plotted figures are **US dollar holdings only**. Silver is tracked
separately in the ledger and is **not** valued in dollars or included in the
charts.
